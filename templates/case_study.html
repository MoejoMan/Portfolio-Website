Cambridge Fibre Ordering Platform

In 2026 I worked as a DevOps Engineer at Netservers on projects for Cambridge Fibre Networks, a full fibre broadband provider in Cambridge. I rebuilt the Odoo backend and, together with the CEO, built the customer website and ordering flow on top of it.

The code is private, so this page describes the design only. Commercial details such as internal thresholds, partner interfaces, and customer data are left out on purpose.

What I built

  • Odoo backend rebuild. Reorganised the custom Python modules and cleared bugs caused by outdated Python and XML. Over 200 merge requests.
  • Address and serviceability engine. A customer enters a postcode and picks an address. The system matches it to its UPRN, decides whether it can be served from its distance to the existing network, and returns the plans available from the company's own network or from a wholesale partner.
  • Live plan data. Odoo sends plans to the website through FastAPI, with Redis and RabbitMQ in the messaging layer. Prices, promo codes, yearly cost, and add ons such as mesh nodes update as soon as the data changes in Odoo.
  • Installation scheduling. With the CEO, an automated scheduler that publishes engineer availability to the website so customers book their own install slot.
  • Order pipeline. A Stripe deposit, a web order created in Odoo, and an engineer scheduled automatically. For partner addresses, the order is placed with the partner as well.
  • One Touch Switching. A working integration between Odoo and the switching hub, built and tested but not released before I left.
  • Customer website. Built with the CEO in Next.js, React, and TypeScript, with Payload CMS for content and Cloudflare Turnstile on forms.
  • Local environment. A Docker replica of the website and backend so changes could be developed and tested safely on a laptop.

The customer journey

  1. Enter a postcode.
  2. Pick an address from the list.
  3. See the plans available for that address, with live pricing.
  4. Add promo codes and extras.
  5. Choose an installation slot from real engineer availability.
  6. Pay the deposit through Stripe.
  7. The order lands in Odoo and an engineer is booked.

How I worked

Every change went through a merge request that the CEO reviewed by hand, was merged into a dev testing version first, and reached production only through him. There was no automated CI pipeline. If I were continuing the project, the first thing I would add is automated tests and CI around the serviceability and pricing rules, since they matter most.
